    Chapter 4

    The Tape

    In chapter 3 we derived every derivative by hand and wrote a function for each. In this chapter the program forms them itself: we write only the forward computation, the way the formulas read, and the way back follows from it.

    Values That Remember Where They Came From

    The backward computation of chapter 3 follows a pattern. Every step forward has a step backward, and which one depends only on what was computed going forward: a matrix product, a sum, a tanh. If every value remembers how it came about, a program can walk that way back without our writing it down. This is called automatic differentiation, and the record it walks is called the tape.

    In our program every value has an entry for it:

    define Entry(kind: int, a: ref[Entry]?, b: ref[Entry]?, value: Matrix,
             var grad: Matrix, var seen: bool)

    kind says what was computed, a and b are the entries the value came from, and value is the value itself, a matrix. The question mark after ref[Entry] means the reference may be missing: a tanh has only an a, and the points and the weights the computation starts from have none. grad is as large as value and takes the derivatives on the way back; seen is needed there too.

    For a matrix A we write these derivatives as a matrix GA of the same size:

    (GA)ij=∂L/∂aij

    The number at place i, j says how strongly the loss L changes when aij changes a little. The D of chapter 3 is such a matrix, a layer's GZ.

    A value of the computation is a reference to its entry, and for values we write the operators * and + ourselves:

    define Value(at: ref[Entry])
{
    operator *(this, other: Value) returns Value
    {
        let m product(this.at.value, other.at.value)
        Value(&# Entry(TIMES, this.at, other.at, m, zeros(m.rows, m.cols), false))
    }

    operator +(this, other: Value) returns Value
    {
        let m plus(this.at.value, other.at.value)
        Value(&# Entry(PLUS, this.at, other.at, m, zeros(m.rows, m.cols), false))
    }
}

    Each computes with the matrices of its two values, with product, the matrix product, and with plus, which adds one row to every row like the bias. For the result it makes a new entry that points to the two. Matrices the computation starts from become values through leaf, and tanh is a function that makes an entry like the operators do:

    function leaf(m: Matrix) returns Value
    Value(&# Entry(LEAF, null, null, m, zeros(m.rows, m.cols), false))

function tanh(x: Value) returns Value
{
    let m apply_tanh(x.at.value)
    Value(&# Entry(TANH, x.at, null, m, zeros(m.rows, m.cols), false))
}

    With them a layer is written like its formulas Z=XW+b and H=tanh⁡(Z), in one line: tanh(leaf(X) * w1 + b1).

    Libraries such as PyTorch keep the tape as a list: every computation appends itself while it runs. In Scaly that does not work. Operators and functions are pure; they return their result and change nothing else, no list outside either. So here every entry points to the ones it came from. Together the entries form a graph that reaches from the loss to the points and the weights, and the order, the tape proper, is made from it only on the way back.

    That leaves the question where the entries live. &# Entry(…) makes an entry and, with &, hands out a reference to it. The # says where, as in zeros: on the caller's page. The operators and tanh are called in step, so all the entries of a learning step lie on its page and go with it, like the matrices in chapter 3. No number is copied on the way: handing on a matrix hands on its sizes and the reference to its numbers, so the entry leaf(net.W1) makes sees the same numbers as the network.

    The Way Back

    At the end of the forward computation stands the loss L, a matrix with a single number, and its derivative by itself is 1. From there the way leads back: every entry hands its derivatives on to the entries it came from. It may do so only once every entry that reads it has given it its share. order puts the entries in an order for that, each after the ones it came from, and backward walks it from the end to the front:

    procedure order(mutable e: ref[Entry], mutable tape: Array[ref[Entry]])
{
    if e.seen
        return
    e.seen := true
    let a e.a
    if a <> null
        order(a, tape)
    let b e.b
    if b <> null
        order(b, tape)
    tape.add(e)
}

procedure backward(mutable loss: Value)
{
    var tape Array[ref[Entry]]()
    order(loss.at, tape)
    loss.at.grad.put(0, 0, 1.0)
    var k tape.length
    while k > 0
    {
        k := k - 1
        back(tape[k])
    }
}

    order goes to a and b first and appends the entry itself only after them. seen makes sure that an entry two computations read comes onto the tape only once. In our network every value is read by just one computation, but this way backward is right for any.

    What an entry hands on depends only on its kind. For the matrix product:

    C=ABGA=GCBT,GB=ATGC

    These are the two products of chapter 3: GCBT is the DWT that hands the loss one layer forward, and ATGC is the HTD, the derivative of the weights. The sum C=A+b hands GC on unchanged, to A and to b; since b was added to every row, it gets the column sums, like the bias in chapter 3. For tanh each number is multiplied by the slope at its place:

    H=tanh⁡(Z)GZ=GH⊙(1−H2)

    And for the loss, the mean over the n points:

    L=1n∑i12(ai−ti)2∂L/∂ai=(ai−ti)/n

    One after the other these rules give the formulas of chapter 3. The loss hands (a−t)/n to the network's answer, its tanh makes (a−t)(1−a2)/n of it, the D of the output, here already divided by the number of points. The sum hands it on to the product and to b3, the product to h2 and to w3, and so on down to the points.

    When two computations read the same value, two derivatives arrive at its entry, and they add up. That is why the rules in the program add to grad instead of setting it. back picks the rule by the entry's kind:

    procedure back(mutable e: ref[Entry])
{
    let a e.a
    if a = null
        return
    if e.kind = TANH
        back_tanh(e.value, e.grad, a)
    let b e.b
    if b = null
        return
    if e.kind = TIMES
        back_times(e.grad, a, b)
    if e.kind = PLUS
        back_plus(e.grad, a, b)
    if e.kind = LOSS
        back_loss(e.grad, a, b)
}

    Each rule is a small procedure. The one for tanh:

    procedure back_tanh(H: Matrix, G: Matrix, mutable a: ref[Entry])
{
    for k in H.rows * H.cols
    {
        let h H.data[k]
        a.grad.data.put(k, a.grad.data[k] + G.data[k] * (1.0 - h * h))
    }
}

    And this is the whole learning step:

    procedure step(mutable net: Net, X: Matrix, T: Matrix, rate: f64)
{
    let w1 leaf(net.W1)
    let b1 leaf(net.b1)
    let w2 leaf(net.W2)
    let b2 leaf(net.b2)
    let w3 leaf(net.W3)
    let b3 leaf(net.b3)
    let h1 tanh(leaf(X) * w1 + b1)
    let h2 tanh(h1 * w2 + b2)
    let a tanh(h2 * w3 + b3)
    var l loss(a, leaf(T))
    backward(l)
    descend(net.W1, w1, rate)
    descend(net.b1, b1, rate)
    descend(net.W2, w2, rate)
    descend(net.b2, b2, rate)
    descend(net.W3, w3, rate)
    descend(net.b3, b3, rate)
}

    The three lines forward read like the formulas, and the backward computation, three lines and four functions in chapter 3, is one call of backward. After it the entry of every weight holds its derivative, and descend moves the weight by it, times the learning rate. Another network, with one more layer or another activation, needs no new backward computation, only a rule for each new kind of computation; the last section tries it. The whole program is on GitHub.

    The Same Numbers

    Does the tape compute right? This chapter's program learns the circle from the same starting weights and with the same learning rate as the one of chapter 3, so it must print the same losses. Nearly all numbers agree digit for digit; three differ:

    StepChapter 3Tape
    100, training0.483253082286431430.48325308228643155
    300, test0.398500796376129840.3985007963761298
    500, training0.19223560940857510.19223560940857506

    The difference is in the 16th or 17th digit, and it has nothing to do with the tape: the program computes in another order. Chapter 3 begins every sum with the bias, the tape adds it last. Chapter 3 divides the finished derivative by the number of points, the tape divides every share before adding it. Mathematically that is the same, but a floating-point number has only 53 binary digits, and every operation rounds to them. In another order the rounding falls in other places. The outcome does not change: both programs get 188 of the 200 test points right.

    The tape is not free. It makes a second matrix for every value, and it also forms derivatives nobody needs, the ones by the points. For 50,000 learning steps it takes 1.65 seconds instead of 1.02, both built with scaly build --release, on the same M1 Pro. Memory does not grow all the same: at most 2.06 MB, for 500 steps as for 50,000, because the entries go with the page of step.

    Another Activation

    What does the tape bring if it computes the same numbers more slowly? It pays off as soon as the network changes. In the two hidden layers, let us take instead of tanh the activation chapter 2 mentioned for large networks, ReLU:

    H=max⁡(0,Z)

    The output stays tanh; it is still to answer between −1 and 1. With the tape ReLU needs what tanh needs: a function that makes an entry, and a rule for the way back.

    function relu(x: Value) returns Value
{
    let m apply_relu(x.at.value)
    Value(&# Entry(RELU, x.at, null, m, zeros(m.rows, m.cols), false))
}

    apply_relu sets every negative number to 0. The slope of ReLU is 1 where the sum is positive, and 0 elsewhere. So the rule hands GH on unchanged where zij>0, and nothing elsewhere. Whether the sum was positive it sees from the answer, since ReLU gives more than 0 exactly there:

    procedure back_relu(H: Matrix, G: Matrix, mutable a: ref[Entry])
{
    for k in H.rows * H.cols
    {
        if H.data[k] > 0.0
            a.grad.data.put(k, a.grad.data[k] + G.data[k])
    }
}

    Add a line in back that calls this rule for the kind RELU, and in the learning step tanh becomes relu in two places: relu(leaf(X) * w1 + b1). That is all.

    Without the tape there would be more to think about. In chapter 3 the slope of tanh sits in two places of the derived backward computation: as 1−h2 in back, for the hidden layers, and in out_share, for the output. We would have to know which of them becomes the slope of ReLU and which stays, and for an operation that does not simply act number by number, derive the chain anew. With the tape every rule stays with its operation, and how the rules chain follows from the network.

    Whether the new rule is right can be checked against the field of chapter 2: its program can do ReLU too, with a backward computation written by hand. From the same starting weights this section's program prints the same losses as the field, again up to the last places.

    It also shows that ReLU learns differently here. After 500 steps only 132 of the 200 test points are right, after 2000 steps 157, and the loss falls only from 0.51 to 0.33 in that time. Then it goes fast: after 2500 steps all 200 are right. With tanh that was so after 1000 steps already. Which activation is better depends on the network and the data, and trying it now takes one word. The program with ReLU is on GitHub.
