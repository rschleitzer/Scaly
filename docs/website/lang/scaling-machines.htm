    Chapter 9

    More Than One Machine

    Where Memory Ends

    Everything so far scaled inside one machine: the cores of the earlier chapters share its memory, and the compiler hands them work on its own. Past the machine's edge memory is no longer shared, a message takes a fraction of a millisecond instead of a few nanoseconds, and the other side may stop answering. Scaly does not hide that edge. A for whose rounds are pure may still cross it: the runtime hands its rounds to copies of the program on other machines where that pays, as it hands them to the cores and to the graphics card. Everything else the program says itself — what goes where — and what it sends is a message.

    A message is a region (Memory That Is Not Shared): a value built on pages of its own, with everything it points to. A send ships those pages as they are, and the receiving side fixes every pointer in them to where the pages landed — with code the compiler generates for each message type. There is no serialization code to write and no schema to keep in step with the program.

    A for over Machines

    The program below counts the primes below three million in blocks: a plain for over the blocks, each round counting the primes of its block and putting the count in its place. Nothing in it says where its rounds run:

    function is_prime(n: int) returns bool
{
    if n < 2
        return false
    var d 2
    while d * d <= n
    {
        if n % d = 0
            return false
        d := d + 1
    }
    true
}

function count_primes(from: int, to: int) returns int
{
    var count 0
    for k in to - from
        if is_prime(from + k)
            count := count + 1
    count
}

let limit 3000000
let blocks 300
var counts Vector[int](blocks as size_t)
for b in blocks
    counts.put(b as size_t, count_primes(limit * b / blocks, limit * (b + 1) / blocks))
var total 0
for c in counts
    total := total + c
print "`total` primes below `limit`"
    $ scaly build --cluster primes.scaly -o primes
$ ./primes --scaly-helper=once &
$ ./primes --scaly-helper=once &
$ SCALY_CLUSTER=on ./primes
216816 primes below 3000000

    Built with --cluster, every for whose rounds can travel is described to the runtime — which part of the program runs a round, and what it reads and writes. Started with --scaly-helper, the same program does not run its main: it announces itself on the local network and waits for rounds. Started as it is, it is the coordinator, and where one of its loops is heavy enough it looks for helpers of its own build, hands each a stretch of rounds, runs stretches itself, and gives a helper that sends one back the next. What the rounds put comes back into the coordinator's vector; inside a stretch a helper uses its own cores, so the inner for of count_primes runs there as it would here.

    Rounds travel where what they read and write can: numbers and records of numbers, vectors, slices and arrays of them read whole, and those they put into at the counter. A reduction, a value a round keeps, a string or a reference keeps the loop on this machine — nothing is said, it runs as before. The count of this program is such a reduction, and so it is added up here, after the loop that went out.

    Whether a loop goes out is measured as the driver measures the cores and the card (When the Cores Are Worth It, Where a Loop Runs): a loop that would take this machine less than 20 milliseconds is never offered; the helpers take part where, with what their stretches cost there and back, they end it a quarter sooner, and what their stretches took teaches the next offer. Here the helpers share the cores of one machine and gain nothing — the runtime would find that out and keep the loop at home —, so the transcript sends it anyway: SCALY_CLUSTER=on sends every loop that can travel, off none, and SCALY_CLUSTER_TRACE=1 shows each stretch and each decision. --scaly-helper=once ends a helper when its coordinator lets go; without it a helper serves one coordinator after the other until it is stopped.

    A helper that goes — its connection closed, or silent past the heartbeat — gives its stretch back, and another runs it; with none left, the coordinator runs the rest. The rounds are pure, so the result does not depend on who ran what. Across machines the helpers hold the cluster's key and run the same build as the coordinator, as every node of this chapter does (One Program, One Build, When a Node Fails). What is not a pure loop stays explicit, and the rest of this chapter is about that.

    Nodes and Channels

    The same count, said explicitly, on three worker nodes. One program plays both roles: started without an argument it coordinates, with one it works. The coordinator listens on a port, hands each worker that connects a share of the range, and prints what comes back:

    define Share
(
    from: int
    to: int
)

define Count
(
    primes: int
    range: String
)

function is_prime(n: int) returns bool
{
    if n < 2
        return false
    var d 2
    while d * d <= n
    {
        if n % d = 0
            return false
        d := d + 1
    }
    true
}

function count_primes(from: int, to: int) returns int
{
    var count 0
    for k in to - from
        if is_prime(from + k)
            count := count + 1
    count
}

procedure work()
{
    let peer Cluster.connect("localhost", 7700, 5000)
    if peer = null
        return
    var shares Remote[Share](peer, 1)
    let counts Remote[Count](peer, 2)
    let share shares.receive()
    if share <> null
    {
        let n count_primes(share.from, share.to)
        counts.send(Count(n, "`share.from` to `share.to`"))
    }
    Cluster.disconnect(peer)
}

procedure coordinate(workers: int, limit: int)
{
    let listener Cluster.listen(7700)
    var peers Array[ref[NodePeer]]()
    var w 0
    while w < workers
    {
        let peer Cluster.accept(listener)
        if peer <> null
        {
            let shares Remote[Share](peer, 1)
            shares.send(Share(limit * w / workers, limit * (w + 1) / workers))
            peers.add(peer)
            w := w + 1
        }
    }
    var total 0
    for peer in peers
    {
        var counts Remote[Count](peer, 2)
        let c counts.receive()
        if c <> null
        {
            print "`c.primes` primes from `c.range`"
            total := total + c.primes
        }
        Cluster.disconnect(peer)
    }
    print "`total` primes below `limit`"
}

if os.arguments().length > 0
    work()
else
    coordinate(3, 3000000)
    $ scaly build primes.scaly -o primes
$ ./primes work &
$ ./primes work &
$ ./primes work &
$ ./primes
78498 primes from 0 to 1000000
70435 primes from 1000000 to 2000000
67883 primes from 2000000 to 3000000
216816 primes below 3000000

    Here the four nodes are four processes on one machine; on four machines the workers name the coordinator's host instead of localhost, and every node is given the cluster's key (below, When a Node Fails). Cluster.connect keeps trying for as long as its last argument says, in milliseconds, because a worker may start before the coordinator listens; Cluster.accept waits for the next node to connect. Either answers the connection to the other node, or null.

    A Remote[T] is a channel to that node for messages of one type, named by a number both sides agree on: here 1 for the shares and 2 for the counts. send hands a message over and returns at once; receive waits for the next one and answers it, or null when the other node has said goodbye or is gone. Cluster.disconnect says goodbye. The coordinator first sends every share and only then collects, so the three workers count at the same time — and each of them counts its share with the plain for of Loops on All Cores, on all the cores of its machine.

    A Message Is a Region

    counts.send(Count(n, "…")) builds the Count — the record and the string in it — on a page of its own, and the send ships that page and releases it. What is sent is gone from the sender; nothing on the other side can point back into it. The receiving node's pages hold the same bytes at other addresses, the generated code fixes the pointers, and receive hands the message to the routine that asked: it belongs to that routine's region from then on and goes when that region goes, like any value the routine built itself.

    Because the send builds the message, its argument is the construction, or a call that makes the message. A value built before would have its string on another page, which the send would not ship, so a name is refused:

    let c Count(n, "`share.from` to `share.to`")
counts.send(c)      ; error: send builds the message on a page of its own

    A message may hold records, unions, strings and the containers of the standard library — Vector, Array, List, HashMap — nested as deep as the program likes. What only makes sense in one process cannot be sent, and the compiler says so: a delegate, an open file, a fixed-size array.

    One Program, One Build

    Pages shipped as they are only make sense to a program that lays out its records the same way. So the nodes of a cluster run one build of one program — which is why the transcript builds once and starts the result four times. Two nodes check it before anything else: each sends a stamp of its build when it connects, and a node whose stamp differs is refused, with both stamps in the error. A new version of the program is a new cluster.

    When a Node Fails

    A node that crashes, loses its network or stops answering looks the same from the other side as one that said goodbye: its channels close, and a receive waiting on one of them answers null. That is why the coordinator asks if c <> null: with a worker killed in the middle of its share it prints the counts of the others and finishes. A silent node is noticed by its silence — the nodes exchange a heartbeat every half second when nothing else flows, and one silent for two and a half seconds is taken for gone. That is a suspicion, not a proof; a node that was only slow finds its connection closed.

    A send never waits for an answer and is never retried: a message arrives at most once, the messages of one channel in the order they were sent, and a message sent to a node that is gone is dropped. Whether a lost share is sent to another worker is the program's decision, not the runtime's. The tests of the cluster runtime include such a program: a small transformer trained on several nodes, each computing the gradients of its part of a batch, one node summing them in a fixed order and sending the sum back. Its loss is the same to the last bit as on one node, and with one worker killed mid-run the others finish the training.

    Who may join is decided before the first message. A cluster without a key stays on one machine: a node listens on the loopback only and refuses a peer from anywhere else. Across machines every node holds the same key — in the environment as SCALY_CLUSTER_KEY, or in the file ~/.scaly/cluster.key — and proves it when it connects, by an HMAC over a challenge of the other side; a node with another key, or none, is refused. One limit is named: the key keeps strangers out, it does not hide what the nodes say to each other. The messages are not encrypted, and a node checks the framing of what it receives, not the meaning — run a cluster across machines only inside a network you trust.
