Trusting the compiler

Scaly's compiler is written in Scaly and built by itself. You do not have to take it on trust: a C++ compiler of your choice can check it.

The question

A compiler that compiles itself can carry something its sources do not say, and hand it on to every compiler it builds. Ken Thompson showed it in 1984, in Reflections on Trusting Trust: reading the sources proves nothing about the binary that compiled them.

Scaly's compiler is built from the seed: the compiler compiled to LLVM IR, committed in the repository's seed/ as text. Every installation that builds from source starts from it, and every new seed is made by the compiler the old one built. So the question is whether the seed is what the sources say.

The answer: a second compiler

The repository also holds the compiler as C++, in trust/. Build it with your C++ compiler, and let the result compile the compiler's sources. If what comes out is the committed seed, byte for byte, then the seed is what the sources say: anything hidden in the seed would have had to be hidden in the C++ too, and the C++ is there to read. This is David A. Wheeler's diverse double-compiling, with your C++ compiler as the second, independent one.

git clone https://github.com/rschleitzer/Scaly && cd Scaly
trust/check.sh                  # build from the C++, emit the seed, compare
CXX=g++ CC=gcc trust/check.sh   # the same with GCC, nothing of LLVM's toolchain
trust/check-gcc.sh              # that, in an AlmaLinux 9 container without clang

It needs a C++20 compiler, a C compiler and LLVM 21 (libLLVM and its headers); no Scaly compiler and no seed. It prints OK when the compiler built from the C++ emits all seven files of seed/ exactly as they are committed — about half a minute on a laptop, a few minutes with GCC in the container.

Every release is checked this way. The release workflow builds the compiler from the C++ with GCC in an AlmaLinux 9 container, with no clang installed, and makes no release of a version whose seed does not come out of it.

What the C++ looks like

It is written by the compiler's second back end (scalyc --emit-cpp), from the same plan the LLVM back end reads: after every decision about types, overloads, integer widths and where a value lives. The C++ shows those decisions written out instead of leaving them to the C++ compiler. A generic routine becomes a template where all its instances agree, character for character:

packages/scaly/0.2.1/scaly/containers/Vector.scaly
function get(this: Vector[T], i: size_t) returns ref[T]?
{
    if i >= length
        return null

    data + i
}
trust/libscaly.cpp
template <class T> static T* Vector_get(Vector<T>& scaly_self, uint64_t i)
{
    Vector<T>* this_ = &scaly_self;
    if ((i >= this_->length))
    {
        return (T*)(nullptr);
    }
    return ((this_->data) + (int64_t)(i));
}

One function per routine, named after it (Planner_lookup_concept), with its symbol as the link name, and a call names its callee — no C++ overloading takes part. No headers: the C library is declared where it is called. The files are generated and never edited by hand; they are written again whenever the seed is, from the same tree.

What it proves, and what stays trusted

Proven: the compiler built from this C++ by your C++ compiler produces the committed seed, so the seed carries nothing the C++ does not.

  • Your C++ compiler. That is the point: pick one that has nothing to do with Scaly. The check passes with Apple clang and with GCC 11.5.
  • libLLVM 21, which the compiler calls to write the IR. Both builds use it, so both would agree on anything it might add.
  • The runtime's few C and assembly files (fiber switching, evented I/O, time, the panic path) and one C++ file that sets WebAssembly's exception model. Both builds compile them as they are.
  • The C++ itself — the thing to read. Who checks a release reads the C++'s diff against the previous one, and it follows the diff of the Scaly sources.
